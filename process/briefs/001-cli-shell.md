# 001 — CLI shell

## Problem

kete needs a CLI for setup, status, search, sync (when sync ships), and operational tasks. The CLI is also how the proxy and MCP server are started: `kete proxy` runs the HTTP server, `kete mcp` runs the stdio MCP server.

The shape of the solution is straightforward: a thin dispatcher that maps subcommands to small handler functions, with one consistent error path that always closes the DB. The interesting question is which Go convention to use, settled in ADR 0010 (cobra).

## Who is hurt

Anyone typing `kete` at a shell. The surface is small enough that getting it wrong is felt on every invocation.

## Constraints

- Subcommand surface (v1):
  - `kete proxy [--debug] [--extended-cache]` — start the HTTP proxy.
  - `kete mcp` — start the stdio MCP server.
  - `kete status` — show captured tasks for the current project (or `--all` for everything).
  - `kete tasks <query>` — search captured tasks by goal/keywords/files.
  - `kete drift-test <prompt> --goal <goal>` — debug drift detection on a fixture.
  - `kete doctor` — diagnose setup (DB perms, upstream reachability, env vars).
  - `kete purge` — wipe local state (with confirmation).
  - `kete --version`, `kete --help`.
- A single error path that always closes the DB. `defer store.Close()` plus a `run()` function returning `error` and a `main` that prints `Error: <msg>` and exits 1.
- `--version` reads from a single build-time source (`-ldflags "-X main.version=…"`), not a duplicated literal.
- Cold start under 50 ms is a soft target, not a release gate (per brief 000).
- No interactive setup wizards. `kete init` is *not* part of v1 — Crush configuration is documented in `docs/how-to/`, not generated by kete.

## Success looks like

- `kete --help` lists the commands in a sensible order (lifecycle commands first: `proxy`, `mcp`, `status`; then operational: `tasks`, `drift-test`, `doctor`, `purge`).
- A failing subcommand prints `Error: <message>` on stderr and exits 1; no partial DB state, no orphaned WAL files.
- `kete status` returns in under 50 ms on a warm cache against a representative DB.

## Non-goals

- Coloured output, spinners, or interactive TUIs. Plain text is the bar.
- Shell completions (cobra gives them for free if we want them later; not a v1 goal).
- A `kete init` subcommand. Setup is documentation, not codified rewriting of someone else's config files.
- Subcommands for cloud-sync features (`login`, `logout`, `sync`). Those land when brief 005 reactivates.
- A `kete agents` debug subcommand. Internal-only; if we need it, we add it under `kete debug` rather than in the top-level surface.

## Open questions

- `[adr]` 0010 — `cobra` vs hand-rolled `flag` dispatch. Settled: cobra.
- Where the search index for `kete tasks` lives. Probably FTS5 on the existing `tasks` table; cheap to add. Defer to plan stage.
- Whether `kete doctor` should sanity-check Crush is configured to point at the proxy. Pro: closes the loop on the most common setup failure. Con: requires reading Crush's config file. Defer; ship reachability check first.
